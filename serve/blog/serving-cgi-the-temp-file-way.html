Serving CGI the temp-file way

2026-05-02 · cgi · K. Ito · all posts

Every CGI tutorial assumes you'll install a scripting runtime and spend an afternoon configuring its process pool. We took a shortcut: the server ships with a tiny native helper binary, and when a request hits /cgi-helper, the server copies that helper to a scratch file and executes it with popen().

How it works

The handler stages the helper at /tmp/dvws_cgi_<pid>, makes it executable, runs it, and streams whatever it prints straight to the socket. Response headers are sent first, so the connection close delimits the body. One binary, no interpreter, zero daemons.

Why it's fine (it isn't)

The scratch filename is derived from the process ID, which is trivially predictable on most kernels. The staged copy is closed and left sitting at that path for a good while before it is executed, so anything that can predict the name -- and write to /tmp -- can race the copy and substitute its own executable. We know. We shipped it anyway, because the whole point of this server is to be the thing you practice on.

When you actually want this

Honestly, never in production. But for a workshop box it keeps the process tree flat -- one server binary, one helper fork per request -- which makes everything observable with plain ps and ls /tmp. For teaching, that transparency is worth more than throughput.

Try it yourself: hit /cgi-helper and then go look for the scratch file while the request is in flight.
