Serving PHP the temp-file way

2026-05-02 · php · K. Ito · all posts

Every PHP setup tutorial assumes you'll install FPM and spend an afternoon on pool configuration. We took a shortcut: when a request maps to a .php file, the server copies it to a scratch file and pipes it through the interpreter with popen().

How it works

The handler writes the script to /tmp/php_script_<pid>.php, runs the interpreter on that copy, and streams whatever the interpreter prints straight to the socket. Response headers are sent first, so the connection close delimits the body. Simple, debuggable, zero daemons.

Why it's fine (it isn't)

The scratch filename is derived from the process ID, which is trivially predictable on most kernels. A second request landing while the file exists reads the same script, and anything that can predict the name can race the copy. We know. We shipped it anyway, because the whole point of this server is to be the thing you practice on.

When you actually want this

Honestly, never in production. But for a workshop box it keeps the process tree flat -- one binary, one interpreter fork per request -- which makes everything observable with plain ps and ls /tmp. For teaching, that transparency is worth more than throughput.

Try it yourself: hit /echo.php and then go look for the scratch file while the request is in flight.
